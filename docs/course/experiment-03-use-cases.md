# 实验三：NoteAgent 用例建模与用例描述

## 1. 建模依据与范围

依据实验二的 NoteAgent 需求清单，本实验聚焦两组核心业务：聊天整理与草稿审核，以及 Markdown 笔记管理与检索。学习者是主要参与者；本地维护者负责故障排查和手动重新索引，**不是**多用户系统中的管理员账号。图中 `FR-xx` 对应实验二需求编号。

用例图描述参与者与系统提供的能力，不表示操作执行顺序。实线表示参与者与用例的关联；虚线箭头 `«include»` 指向必含用例，`«extend»` 指向被条件扩展的基础用例。异常处理和步骤顺序在下方用例描述中说明。

## 3. 核心用例描述

### UC-01 请求整理笔记

| 项目 | 描述 |
| --- | --- |
| 参与者 | 学习者 |
| 对应需求 | FR-02 |
| 前置条件 | 学习者已进入聊天页面；模型服务可用。 |
| 触发条件 | 学习者明确提出创建、追加、替换或删除笔记的要求。 |
| 基本流程 | 1. 学习者输入整理要求。2. 系统生成含目标文件、操作类型和内容的待审草稿。3. 系统向学习者展示草稿。 |
| 异常流程 | 模型调用失败时，系统显示错误，不创建虚假的成功结果。 |
| 后置条件 | 草稿待审；正式笔记尚未改变。 |

### UC-02 审核待审草稿

| 项目 | 描述 |
| --- | --- |
| 参与者 | 学习者 |
| 对应需求 | FR-03、NFR-01 |
| 前置条件 | 当前会话存在待审草稿。 |
| 触发条件 | 学习者查看草稿并选择确认或拒绝。 |
| 基本流程 | 1. 学习者核对目标文件、操作类型和内容。2. 选择确认。3. 系统写入正式笔记，并尝试更新检索索引。4. 系统显示保存结果。 |
| 备选流程 | 学习者选择拒绝，系统结束本次审核，正式笔记保持不变。 |
| 异常流程 | 写入失败时显示错误并保留可恢复的待审草稿；索引失败与笔记保存结果分开显示。 |
| 后置条件 | 成功确认后笔记变更；拒绝或写入失败时正式笔记不因本次审核而变更。 |

### UC-03 编辑 Markdown 笔记

| 项目 | 描述 |
| --- | --- |
| 参与者 | 学习者 |
| 对应需求 | FR-04、FR-07 |
| 前置条件 | 目标 Markdown 笔记存在于 `notes/` 范围内。 |
| 触发条件 | 学习者打开并修改笔记后点击保存。 |
| 基本流程 | 1. 系统显示笔记内容。2. 学习者修改正文。3. 系统保存 Markdown 文件。4. 系统尝试更新对应索引并显示结果。 |
| 异常流程 | 保存失败时显示错误；索引失败时显示未索引状态，不宣称索引成功。 |
| 后置条件 | 保存成功后重新打开可看到最新内容。 |

### UC-04 检索已有笔记

| 项目 | 描述 |
| --- | --- |
| 参与者 | 学习者 |
| 对应需求 | FR-06 |
| 前置条件 | 系统存在可用的笔记检索索引。 |
| 触发条件 | 学习者询问以前记录过的知识点。 |
| 基本流程 | 1. 系统按问题检索笔记片段。2. 系统基于命中的内容回答。3. 回答使用片段时，显示可定位的笔记来源。 |
| 备选流程 | 没有命中时，系统说明未找到依据。 |
| 异常流程 | 检索服务失败时，系统报告错误，不把故障表示为“没有相关笔记”。 |
| 后置条件 | 正式笔记不因检索而改变。 |

### UC-05 手动重新索引

| 项目 | 描述 |
| --- | --- |
| 参与者 | 本地维护者；学习者在本地维护时也可承担该角色。 |
| 对应需求 | FR-07 |
| 前置条件 | 目标笔记存在，且索引缺失或需要修复。 |
| 触发条件 | 参与者从索引状态入口选择重新索引。 |
| 基本流程 | 1. 系统读取目标笔记。2. 系统重建对应索引。3. 系统显示更新后的索引状态。 |
| 异常流程 | 重建失败时保留原笔记，并显示失败状态与可定位的错误信息。 |
| 后置条件 | 成功时目标笔记可参与后续检索；失败时正式笔记不变。 |

## 4. 报告使用建议

本次使用本机 draw.io 桌面版建模：新建图页，放置系统边界、参与者和椭圆用例，连接关联及 `«include»`、`«extend»` 关系，保存为 `.drawio`，再导出 PNG。打开上表中的源文件即可在 draw.io 中继续编辑。实验报告可用两张导出的 PNG 作为建模成果截图，并注明软件名称和文件路径。

在实验报告中分别插入两张 PNG，并在图下说明参与者、主要用例及 `«include»`、`«extend»` 的含义。提交仓库时保留 `.drawio` 源文件，便于教师检查和后续修改。图中只标记功能需求编号；非功能需求在用例描述和后续测试中验证。
